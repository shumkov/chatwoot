Status: deployed and activated on 15 October 2026; Nastya access and browser acceptance remain open.
Owner request: close the report task, keep influencer/collaboration work out of Mai's individual reminders, show one aggregate Orders reminder with a count and a label-filter link, and notify about new customer work without waiting ten minutes.

## Decisions and business behavior

1. The Notion report task is Done (persisted readback verified). Other project tasks retain their IDs and statuses until work starts/completes.
2. Route each current obligation by its purpose, not by the person's influencer role. Customer purchase/after-sales work belongs to Mai. Partnership, influencer/barter collaboration and content work belongs to Nastya. A thread can contain both. The existing influencer customer-role field and Klaviyo sync remain unchanged. Social mentions, personal exchanges, thanks with no outstanding question, tests and marked spam are not work.
3. Reuse the existing full-history reminder analysis. Add `queue: customer|collaboration` to each task; no second classifier, agent, inbox, team, routing table or database. `needs_reply` still describes the whole conversation; derive customer/collaboration reply obligations from validated reply tasks. Preserve stable task IDs, dates, evidence, resolved/snoozed boundaries and operator corrections already in use.
4. One system-maintained conversation label, `collaboration-pending`, means there is actionable collaboration work now. It is NOT the persistent influencer role and NOT an unread/read flag. An acknowledged proposal can still require an internal decision; therefore the aggregate says “N collaboration conversations need attention — Nastya”, not “N people have not been read”. Include any current unsnoozed collaboration obligation, but scheduled future work only when due. Count distinct conversations, not tasks or people. Replying clears the label only when no collaboration work remains. Resolve clears current work; Snooze temporarily removes it; a separately scheduled follow-up returns only when due. Opening a conversation does not finish work. Shumabit never changes conversation status or snooze time automatically: an unanswered collaboration stays Open; the operator uses Snooze for a deliberate delay and Resolve only after completion or a decision not to proceed.
5. Send one aggregate message per Bangkok business day in UMI Team → Orders, on the first nonempty queue check (09:00 for an overnight backlog). Edit that same message as the count changes; do not send individual collaboration notifications or a new message on every count change. At zero, edit it to “Collaboration queue clear” and mark completed. If new work appears later that day, update the same message. No daily message for an empty queue. Link: `https://chat.umi.store/app/accounts/1/label/collaboration-pending?status=all&assignee_type=all`. The current label view defaults to Mine and restores saved status, so implement narrowly scoped deep-link filter support: honor validated explicit status/assignee query parameters on label routes before the first fetch and at route navigation, without writing user preferences or changing ordinary routes. Restore ordinary saved/default filters when leaving the explicit-query context; test invalid/partial parameters and navigation away/back. Invalid parameters retain existing defaults. Native account/inbox permissions still apply; verify Nastya has access to the intended inboxes rather than widening permissions. No new screen or visual redesign. Saved folders are user-owned in this version and cannot supply one shared team link.
6. Customer notification: one first notice per new unanswered incoming burst after the feature cutover, as soon as a fresh analysis identifies customer work. Do not wait for ten minutes. Consecutive messages before the operator replies remain one burst; a later question after a reply starts another. At ten working minutes send one overdue notice if still actionable. If first classification arrives after ten minutes, send only the overdue notice and consume the first-notice key as well. Preserve completion edits/reactions and existing non-reply promise/due-work reminders. Avoid duplicating a first notice as an hourly reply task.
7. Keep daily 09:00–21:00 Bangkok delivery hours. Overnight customer messages appear in the 09:00 queue, not as both a first notice and morning message. The five-business-minute response target and ten-minute escalation threshold do not change.
8. Run the existing analyzer each minute instead of every five minutes; continue analyzing changed histories only, under its existing exclusive lock. Prioritize new unanswered/unrouted work over older refreshes, retaining eventual processing for other changed rows. This is prompt notification after routing, normally on the next analysis cycle, NOT a guaranteed sub-minute or webhook notification. Inference can take up to 90 seconds per conversation and a run up to four minutes. Fresh routing is required to avoid alerting Mai for a new collaboration. During unavailable analysis, do not invent routing or treat stale collaboration classification as evidence for a new customer question; expose the delayed assessment in existing technical health checks. This deliberately replaces the generic per-conversation fallback alert when routing is unknown. Native Chatwoot notifications remain available and unchanged.

## Research and alternatives

Current producer: `umi/app/services/funnel/operator_queue.rb` provides complete retained history, revision-bound rows, waiting bursts and closure boundaries. Current consumer: Shumabit `scripts/crm-operator-reminders.js` uses separate analyze/tick jobs, durable send receipts and presentation edits. Live schedule readback on 15 October confirms tick each working minute, analyzer every five minutes. Last read tick was healthy; analyzer health reported unavailable and requires diagnosis before activation, not a guessed success.

Current prompt explicitly puts genuine influencer collaborations in Mai's checklist. Filtering the influencer customer label alone would also hide their purchases/returns; rejected. A manually maintained unread label would drift from actual work and require duplicate operator bookkeeping; rejected. Existing Chatwoot status plus a derived queue label is enough. Individual instant alerts for every raw incoming message would reproduce social/spam/collaboration noise; rejected in favor of prompt post-analysis notices. A new webhook service could reduce polling latency but adds a second workflow and is unnecessary for this iteration.

Official Chatwoot docs support labels and label filters: https://chatwoot.help/hc/user-guide/articles/1677496066-how-to-add-labels and https://app.chatwoot.com/hc/user-guide/articles/1677698771-group-chats-with-filters-save-as-folders . The checked source exposes `/app/accounts/:accountId/label/:label`. The ordinary conversation-label POST replaces the full list (`LabelConcern#create`); read-modify-write can lose concurrent ordinary label edits. Native macros are asynchronous and cannot validate the original judgment revision. Reuse locked incremental label methods through a small UMI endpoint instead. Upstream issue documenting the same API limitation: https://github.com/chatwoot/chatwoot/issues/15916 .
