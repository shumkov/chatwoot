# UMI CRM: поля, лейблы, интерфейс и автоматизация

29 сентября 2026. Согласованный подход: штатный интерфейс без доработок, атрибуты как источник фактов, управляемые лейблы для их видимости и private notes для полной сводки. Переписанный контракт перед реализацией; новые правила ещё не развернуты.

Полный план первого этапа и порядок внедрения: [UMI-FUNNEL-STAGE-ONE-SPEC.md](UMI-FUNNEL-STAGE-ONE-SPEC.md). Этот документ — актуальный источник правил о типах данных, лейблах, видимости и синхронизации. Он заменяет соответствующие предварительные решения в UMI-CONVERSATION-LIFECYCLE-DECISIONS.md и UMI-LABEL-TAXONOMY-SPEC.md. Границы диалогов, рекламная атрибуция, модель и проверенные operational receipts остаются в lifecycle decisions. Ошибка мобильного превью Reels описана отдельно в UMI-MOBILE-REEL-PREVIEW-DIAGNOSIS.md и не является частью CRM-схемы.

Дополнение от 4 октября 2026: роли Model и Influencer обогащаются административными Shopify-тегами, а история помеченных бартерных заказов передаётся отдельно от покупок. Источник правил тегов, пересечений и порядка поставки — [cross-repository spec](https://github.com/shumkov/umi-vps-infra/blob/main/docs/UMI-COLLABORATION-TAGS-SPEC.md). `Partner` означает место покупки, а не роль человека. Поставка дополнения подтверждается отдельным production readback.

## 1. Правило выбора: атрибут, тема, управляемый лейбл

1. **Контакт хранит, кто человек; диалог — что происходит в обращении; Shopify — заказ и оплату.** Повторный клиент не означает новую продажу в текущем диалоге.
2. **Атрибут — типизированный факт.** Стадия продажи, стадия покупателя, число оплат, VIP/Influencer/Model/Wholesale/High value и их явное «Нет/Неизвестно». VIP и Influencer — разные вопросы: два отдельных атрибута могут одновременно иметь «Да».
3. **Обычные лейблы — набор тем одного диалога.** Например, размер + цвет + возврат. Их применяют AI/оператор; новый диалог не наследует темы предыдущего.
4. **Управляемые лейблы — отображение определённых фактов.** Десять customer labels вычисляются из атрибутов контакта; lead-qualified/lead-converted — из стадии диалога; source-paid-ads — из факта referral. Это не вторые независимые значения. Их не читаем обратно как команду изменить атрибут, платежи или CAPI.
5. **Направление для отображения одно:** факт → управляемый лейбл. Направление для пяти профильных ролей другое: атрибут Chatwoot ↔ свойство Klaviyo. Нельзя смешивать эти два процесса.
6. **Новый интерфейс не нужен.** Используем существующие лейблы очереди, детали/атрибуты и private notes. Не создаём Vue-сводку, новую панель, форк мобильного приложения или систему разрешений.
7. AI и наш worker могут менять и атрибуты, и лейблы; отсутствие штатного действия «записать атрибут» в native rules не мешает выбранной схеме.

Пример: Repeat + VIP пишет про возврат. У контакта Repeat и VIP; у нового диалога not_sales и support-refund; в его label_list автоматически появляются repeat и vip. Никакой новой покупки или Meta-конверсии это не создаёт.

## 2. Словарь полей и источники истины

| Объект / поле | Тип и значения | Кто пишет | Где используется |
|---|---|---|---|
| Диалог: штатный status | open / pending / snoozed / resolved | Оператор и явно согласованные рабочие правила | Очередь обработки; не стадия продажи |
| Диалог: umi_sales_status | enum: unevaluated / engaged / qualified / inactive / not_sales / order_placed / purchased | AI/оператор для смысла обращения; Shopify-связь для order_placed/purchased | Панель, фильтры, неизменяемые события квалификации/оплаты |
| Контакт: umi_funnel_stage | enum: unclassified / non_buyer / chooser / seeker / client / repeat | Подтверждённая история покупок + актуальное членство в сегментах Klaviyo | Единая видимая стадия клиента и управляемый лейбл |
| Контакт: umi_paid_order_count | число или неизвестно | Тот же расчёт | Атрибут и private note; не native Shopify orders_count |
| Контакт: umi_paid_history_complete | boolean, с явным состоянием отсутствующих данных | Тот же расчёт | Ограничение уверенности в истории |
| Контакт: umi_payment_snapshot_at | время | Тот же расчёт | Свежесть истории |
| Контакт: umi_vip | отдельный enum unknown / yes / no | Оператор в Chatwoot/Klaviyo; согласованное правило, если оно появится | Управляемый лейбл, private note и сегменты |
| Контакт: umi_influencer | отдельный enum unknown / yes / no | Оператор; согласованные Shopify-теги заполняют неизвестное; AI может установить yes из unknown по явным свидетельствам | Управляемый лейбл, private note и сегменты |
| Контакт: umi_model | отдельный enum unknown / yes / no | Оператор; явный Shopify-тег model заполняет неизвестное; AI не назначает | Управляемый лейбл, private note и сегменты |
| Контакт: umi_barter_history | boolean; отсутствует/null — неизвестно | Расчёт по помеченным бартерным заказам текущего подтверждённого Shopify-клиента → Klaviyo → Chatwoot | Read-only факт, лейбл barter только при true и private note; не покупка |
| Контакт: umi_wholesale | отдельный enum unknown / yes / no | Оператор; AI может установить yes из unknown по явным свидетельствам | Управляемый лейбл, private note и сегменты |
| Контакт: umi_high_value | отдельный enum unknown / yes / no | Оператор; автоматический порог пока не определён | Управляемый лейбл, private note и сегменты |
| Диалог: intent-* / support-* | Набор разрешённых тем, см. ниже | AI и оператор | Темы обращения, фильтры и отчёт по лейблам |
| Диалог: meta_ad_id/ref/title | Существующие атрибуты + исходный referral в сообщении | Интеграция канала | Реклама/источник; не ручное присвоение продажи |
| Контакт: Shopify/Klaviyo IDs | Существующие внутренние идентификаторы связи | Проверенное сопоставление или действие оператора | Связь карточек, не свободные UI-теги |
| Диалог ↔ draft/order | Существующая отдельная связь с объектом Shopify | Ссылка checkout с атрибуцией или действие оператора | Оплата конкретного обращения |
| Контакт: Instagram audience/followers | Существующий enum/число | Существующая интеграция профиля | Контекст; не доказательство VIP или influencer |

Техническое свойство Klaviyo umi_buyer_lifecycle сохраняет уже реализованные правила: repeat — как минимум две подтверждённые оплаты; client — одна при полной истории; non_buyer — ноль при полной истории; иначе unclassified. При неполной истории и двух подтверждённых оплатах Repeat допустим, но число показываем как «не менее 2», рядом — неполная история. Ранее подтверждённую покупку не стираем из истории из-за последующего возврата; впервые увиденный неоднозначный refund остаётся на проверке по существующему алгоритму. TBYB, неоплаченный pickup, draft или созданный заказ сами по себе не делают человека покупателем.

Поля истории покупок доступны для чтения. Ручное изменение через штатный API атрибутов отклоняется сервером с понятной причиной. Штатный клиент может продолжать показывать редактор; мы не обещаем менять или скрывать его. Описание поля указывает, что значение рассчитано автоматически. Это защита достоверности фактов, без новой системы ролей/разрешений.

В Chatwoot показываем один атрибут стадии клиента — umi_funnel_stage. Исходный umi_buyer_lifecycle сохраняем в техническом снимке контакта (additional_attributes), не создаём второй похожий dropdown.

Роли показываются тремя значениями, поскольку нативный checkbox визуально не различает «не знаем» и «нет». В Klaviyo те же пять ключей имеют true / false / отсутствие свойства; преобразование детерминировано. Значение unknown/удаление — явный сброс, false/no — явное отрицание. AI не меняет установленное no, не снимает yes. Сброс в unknown разрешает новую оценку по свежим сообщениям.

## 3. Полный разбор существующих 27 лейблов и целевые названия

| Группа | Решение первого этапа |
|---|---|
| intent-size-advice, intent-color-advice, intent-product-details, intent-ready-to-order | Остаются темами диалога; AI применяет после проверки качества |
| support-order-tracking, support-exchange, support-refund, support-complaint, support-after-sales | Остаются темами диалога; AI применяет после проверки качества |
| support-special-request | Добавляем в проверяемый набор как явно нестандартную просьбу (например, изменение изделия или специальная упаковка), не как универсальную метку неизвестности |
| intent-interested | Не генерируем дальше: это уже engaged в sales status |
| intent-waiting-reply, intent-waiting-payment | Не генерируем как темы: это временное рабочее состояние. Оплата видна у связанного заказа; очередь ответов — в штатном UI. Новую машину состояний ожидания в этот этап не вводим. Это осознанное отличие от исходного списка Линь, а не обещание реализованных waiting-автоматизаций |
| lead-qualified, lead-converted | Только управляемые зеркала umi_sales_status: qualified → первый, purchased → второй, иначе ни одного. При purchased первый снимается. Прямое редактирование этих зеркал не меняет стадию; оператор меняет поле стадии |
| lead-new, lead-lost, lead-unqualified | Удаляем при миграции; новые автоматы их не ставят. Аналоги — unevaluated/inactive/not_sales, но это не инструкция механически пересчитать старую историю. Если старое правило lead-new включено, выключаем его при переходе на новую схему |
| value-first-time → client, value-returning → repeat | Управляемые отображения buyer lifecycle: client → client, repeat → repeat, иначе ни одного. Client означает ровно одну подтверждённую покупку при полной истории, не анонимного нового собеседника |
| value-vip → vip, value-influencer → influencer, value-wholesale → wholesale, value-high-value → high-value | Управляемые отображения соответствующих контактных полей. yes → лейбл присутствует; no/unknown → отсутствует. Отсутствие лейбла само по себе не различает no и unknown; точное значение остаётся в атрибуте |
| source-paid-ads | Производная метка для штатных отчётов: «в этом диалоге зафиксирован хотя бы один подтверждённый рекламный referral». Это не первый источник привлечения и не выбранный touch квалификации; их алгоритмы отдельно в lifecycle decisions |
| source-organic | Удаляем при миграции; в первом этапе автоматически не генерируем, поскольку отсутствие referral не доказывает organic. Источник без достаточных данных остаётся неизвестным |
| spam | Отдельная модерационная метка. not_sales не означает spam; друзья бренда, инфлюенсеры и поддержка не спам |

Темы описывают «о чём говорили в этом обращении», а не «что сейчас требуется сделать». Поэтому ready-to-order может остаться в истории уже оплаченного диалога, а exchange может добавиться позднее. Текущее состояние показывают атрибуты/заказ. Новый диалог не наследует старые темы. Снятый оператором ошибочный topic не восстанавливаем на том же/старом доказательстве; повторное добавление допустимо только при новой относящейся к нему реплике. Прямые правки лейблов должны попадать в этот контракт корректировок, а не обходить его.

Устаревшие lead-new/lead-lost/lead-unqualified/intent-interested/intent-waiting-*/source-organic удаляем из каталога и назначений, включая закрытые диалоги. Старые value-* заменяем целевыми именами и также удаляем. Сначала прекращаем их запись и сохраняем приватный before-image; legacy-разделов и видимых алиасов не остаётся. Точный порядок в полном плане первого этапа. Нативные отчёты по лейблам не являются историей платежей или достоверной customer segmentation; изменение отображаемого customer label меняет такую группировку.

### 3.1 Управляемые customer labels: точный контракт

| Атрибут контакта | Отображаемый лейбл |
|---|---|
| umi_funnel_stage = client | client |
| umi_funnel_stage = repeat | repeat |
| umi_funnel_stage = chooser | chooser |
| umi_funnel_stage = seeker | seeker |
| umi_funnel_stage = non_buyer / unclassified / отсутствует | Ни одной из четырёх меток стадии клиента |
| umi_vip = yes | vip |
| umi_influencer = yes | influencer |
| umi_model = yes | model |
| umi_barter_history = true | barter |
| umi_barter_history = false / null / отсутствует | Метки barter нет |
| umi_wholesale = yes | wholesale |
| umi_high_value = yes | high-value |
| Любая роль = no / unknown / отсутствует | Соответствующего role label нет |

- Проецируем только эти десять меток и никогда не заменяем весь label_list. Сохраняем темы, spam, source и независимые пользовательские метки. Четыре метки chooser/seeker/client/repeat взаимоисключающие.
- Охват: канонический контакт account 1 и его активные диалоги open/pending/snoozed во всех каналах. Это отображение фактов, не расширение AI-классификации за pilot inbox 2. Отдельные дубли контакта не получают чужие признаки.
- При создании нового диалога проецируем известные локальные атрибуты в его начальном сохранении без ожидания удалённого Klaviyo. При переоткрытии перечитываем актуальные локальные факты. При позднем сопоставлении/изменении атрибутов ставим job обновить активные диалоги; целевое применение локального изменения — в течение минуты при здоровой очереди. Не обещаем атомарно обновить все диалоги одним HTTP-запросом.
- Worker читает текущие атрибуты и текущую связь заново при применении, а не значения из старой queued payload. Проекция берёт блокировки в существующем порядке contact → conversation; под блокировкой диалога повторно проверяет status/identity и меняет только управляемое подмножество текущего списка. Обычные UI/API/bulk-записи лейблов также проверяют актуальный список и сохраняют его под той же блокировкой conversation: штатная полная замена label_list сама по себе такой защиты не даёт. Устаревший запрос, затрагивающий уже изменённые управляемые метки, явно отклоняется; успешная правка темы не затирается проекцией. Старый job не восстанавливает отменённую роль. Обычное открытие страницы не пишет данные и не создаёт заметку.
- На разрешённых/закрытых диалогах customer labels — последний применённый снимок, не обещание текущего статуса клиента. Регулярные изменения VIP их не переписывают. Закрытие финализирует локальную проекцию и status под той же блокировкой; worker повторно проверяет status внутри блокировки и не пишет в уже закрытый диалог. При переоткрытии проекция актуализируется. Отдельное исключение: исправление ошибочной идентичности снимает принадлежащие неверной связи customer labels и из затронутых закрытых диалогов; исходный snapshot/заметка сохраняется как история исправления. Квалификации/оплаты и темы этим действием не переписываются.
- Вместе с применённой проекцией сохраняем её владельца: contact ID, идентичность профильной связи (или отсутствие внешней связи) и применённый набор customer labels. Исправление identity очищает только проекцию, принадлежащую ошибочной связи. До структурной миграции старые ручные метки без такой записи не приписываем неверной связи по одному имени. Миграция сохраняет их только в private before-image и удаляет устаревшие назначения из UI, включая resolved. Это минимальный учёт происхождения, без новой системы разрешений.
- Изменение yes → no/unknown снимает соответствующую метку с активных обращений. Смена client → repeat снимает client и добавляет repeat. label change сам по себе не вызывает профильный update, классификацию или conversion event.
- Синхронизация через Klaviyo не обязательна для локального контекста: обоснованные role-атрибуты несопоставленного контакта могут отображаться локально, пока remote sync ждёт точной связи. Отсутствие buyer identity не превращается в non_buyer.
- При запуске делаем ограниченную сверку активных диалогов по уже известным контактным фактам. Это не AI-разметка архивов. Существующие ручные customer labels не импортируем автоматически в profile attributes. До первого приведения к контракту сохраняем прежние customer labels в private migration manifest; затем заменяем только управляемое подмножество расчётным. Не создаём массовые legacy notes. Одна обычная актуальная customer summary появляется по штатному правилу. Оператор может подтвердить старую роль через атрибут. Структурная очистка названий охватывает и закрытые обращения; это исключение из обычной неизменности снимков, а не AI-разметка архивов. Их текущими фактами покупателя заново не размечаем.
- Прямые обычные UI/API/bulk-правки десяти customer labels и lead-qualified/lead-converted/source-paid-ads отклоняются сервером с указанием редактировать соответствующий атрибут/факт. Это единственный разрешённый путь исправления: не создаём альтернативную трактовку «снятие метки = no». Запрос темы с неизменными управляемыми метками разрешён. Все внутренние писатели проходят те же правила через соответствующую проекцию; native UI не требует нового редактора. Отказы должны быть видны штатным клиентом, а не замалчиваться.

Роли Influencer и Model независимы: у одного человека могут одновременно быть обе роли и платные покупки. Shopify обогащает только неустановленные роли; явные true/false не перезаписываются. Ручное no отвергает предложение, unknown разрешает повторное обогащение. Barter history пересчитывается по заказам и не меняет роль, VIP, paid count или CAPI. Удаление исходного тега/смена связи снимает факт на следующей синхронизации; отсутствие поля означает неизвестно, даже при свежем payment timestamp. Просроченный снимок сохраняет последние факты с предупреждением. Служебная заметка прямо говорит «order marked barter», не обещает оплату или доставку; простое обновление времени не создаёт новую заметку.

### 3.2 Единые названия с воронкой Miro / Klaviyo

Отображаемые названия согласованы с уже используемыми сегментами Klaviyo: **Chooser / Seeker / Client / Repeat**, лейблы Chatwoot — `chooser` / `seeker` / `client` / `repeat`. Внутренние значения `umi_buyer_lifecycle=client/repeat` не меняются. `first-purchase` не используем: оно звучит как событие текущего заказа. Client означает одну подтверждённую покупку при полной истории, Repeat — минимум две. В private note пишем прямо: «Клиент: 1 подтверждённая покупка» или «Повторный клиент: 2 подтверждённые покупки» с оговоркой полноты истории при необходимости.

Сохранённая 27 сентября сверка Miro описывает Stranger → Familiar → Chooser → Seeker (Attention seeker) → Client → Repeat (Repeat buyer). Это путь клиента, отдельно от стадии продажи **текущего диалога**. Repeat может одновременно обсуждать новый заказ или возврат; sales status не заменяет его жизненный цикл.

| Этап Miro / Klaviyo | Основание | Отображение в текущем контракте Chatwoot |
|---|---|---|
| Stranger / Familiar | Аудитории охвата/вовлечения; часто анонимные | Не присваиваем человеку из отсутствия данных |
| Chooser | Подтверждённый non_buyer, сайт/товар за последние 30 дней, без корзины/checkout за это окно | `chooser`, из проверенного членства в Klaviyo |
| Seeker | Подтверждённый non_buyer, корзина или checkout за последние 30 дней | `seeker`, из проверенного членства в Klaviyo; квалифицированный DM сам по себе не равен Seeker |
| Client | Одна подтверждённая покупка, полная история | `client` |
| Repeat | Минимум две подтверждённые покупки | `repeat` |

Chooser/Seeker в существующем коде Klaviyo требуют свежего платёжного снимка. Не вычисляем их заново по тексту диалога и не записываем в `umi_buyer_lifecycle`: это сегменты покупательского поведения, а поле содержит только историю покупок. Их отображение согласовано для первого этапа. Источник — Klaviyo, приоритет Seeker над Chooser только для подтверждённого non_buyer; Client/Repeat не сбрасываются из-за нового просмотра или корзины. Успешно прочитанное отсутствие в обоих сегментах даёт non_buyer без лейбла стадии. Ошибка/неполная пагинация не считается выходом из сегмента: сохраняем последнее подтверждённое отображение с отметкой устаревания; первую непроверенную membership не применяем. Новая подтверждённая покупка сразу имеет приоритет над запаздывающей membership. В техническом снимке сохраняем IDs сегментов, наблюдённое членство и checked_at; плановое чтение не реже 15 минут, но не обещаем мгновенный пересчёт самой Klaviyo.

При внедрении создаём/используем десять целевых customer labels без value-. Сохраняем before-image вне рабочих карточек, удаляем устаревшие определения и назначения во всех состояниях диалогов/контактов и отключаем старых писателей. На активных диалогах применяем подтверждённые факты. Не присваиваем сегодняшнюю стадию закрытой истории. Устаревших видимых алиасов не оставляем; события Meta и исторические оплаты не переписываем.

## 4. Что оператор видит в штатном интерфейсе

На скриншоте пользователя лейблы уже видны под превью сообщения. В исходном коде мобильного LabelIndicator.tsx число видимых лейблов ограничено шириной, порядок зависит от каталога allLabels. Поэтому **не обещаем, что VIP и Repeat всегда оба поместятся**, и не пытаемся обойти это новыми префиксами, переименованием каталога или frontend-патчем.

- В очереди — обычные conversation labels, включая управляемые customer labels после проекции. Это быстрые ориентиры; ряд может показывать только часть меток.
- В диалоге — штатный список лейблов/детали и короткая private note со всей известной сводкой. Если приложение скрывает часть меток в превью, информация не теряется: она есть в note и штатных деталях.
- В атрибутах контакта — точные значения ролей, buyer lifecycle/count/coverage, timestamps и ссылки. В веб-версии они доступны из боковой панели диалога, без перехода на отдельную страницу клиента. Возможности редактирования enum-полей в используемой версии iOS проверяем отдельно; если редактор отсутствует, используем существующую веб-карточку, а не строим мобильный форк.
- История неизвестна или контакт ещё не сопоставлен → нет client/repeat label; в private note явно «история покупок не подтверждена». Одно отсутствие лейбла не является доказательством отсутствия покупок.
- При ошибке refresh сохраняем последние подтверждённые значения и их timestamps. Через 15 минут без успешного обновления профиля считаем его данные устаревшими; для оплаты отдельно используем umi_payment_snapshot_at и существующее двухчасовое окно свежести. Не снимаем Repeat/VIP только из-за timeout. В активном диалоге одна private note сообщает о переходе в устаревшее/ошибочное состояние, следующая — о восстановлении; неизменная ошибка каждую минуту не повторяется. Лейблы сами по себе не показывают свежесть.

Иллюстрация возможного отображения, если ширины хватает (не обещание нового layout):

```text
Анна
Хочу вернуть платье
• vip  • repeat  • support-refund

Внутри диалога — private note:
Покупатель сопоставлен. Повторный клиент, 2 подтверждённые оплаты.
VIP: да. Источник: Klaviyo. Проверено 4 минуты назад.
```

Отдельный Contact label не заменяет conversation label и сам не появляется на всех разговорах. Пользуемся именно управляемой проекцией в conversation.label_list. В первом этапе нет новой строки значков, новой панели или собственного мобильного релиза.

## 5. Когда появляются данные и служебные заметки

1. При входящем сообщении используем существующий contact/channel identity. Если контакт уже связан, начальные управляемые лейблы формируются из локальных данных, независимо от запроса к Klaviyo. Первую summary note создаёт job после commit входящего сообщения/диалога, с устойчивой дедупликацией и повтором через существующую очередь. Сбой этой заметки не откатывает и не теряет сообщение клиента.
2. Для неизвестного контакта запускаем проверяемое сопоставление по доступным идентификаторам или оператор выбирает покупателя. Совпадение имени не создаёт связь. Пока связи нет — «не сопоставлен», а не «новый покупатель».
3. После успешного сопоставления загружаем buyer history и общие признаки; управляемые лейблы обновляются и добавляется новая note. Если внешний сервис недоступен, связь может быть подтверждена, но история помечена как ещё не загруженная.
4. При новом диалоге известного контакта добавляем одну короткую private note со сводкой; если сопоставление случилось в уже открытом диалоге — одну заметку о сопоставлении и полученных данных. Открытие экрана оператором само по себе заметок не создаёт.
5. При материальном изменении фактов в активном диалоге добавляем заметку с изменением. Обычный refresh с теми же данными не создаёт заметок. При разрешении неопределённости или исправлении связи заметка явно уточняет предыдущее состояние, не переписывает его задним числом. Закрытые диалоги не засыпаем новыми заметками.

Пример после подтверждённого сопоставления:

> Система: найден и связан профиль покупателя. Повторный клиент: 2 подтверждённые оплаты. VIP: да, из Klaviyo. История покупок не означает продажу в этом обращении. Карточка Shopify: …

Пример AI:

> AI-классификация: добавлена тема «Возврат». Стадия обращения: не продажа. Покупатель остаётся Repeat / VIP.

Заметки фактологические и шаблонные, без дополнительного LLM-вызова. Они отправляются существующим системным путём, не выдают себя за лично отвечающего Shumabit. Ассистент Shumabit видит их и использует в ответе на @shumabit. Для создания таких заметок не требуется постоянно запущенная агентская сессия на каждый диалог. Если UI должен показывать бренд Shumabit, автор всё равно явно обозначается как автоматическое обновление системы.

Дедупликация по диалогу и реальному изменению/идентичности; одна заметка для совместного изменения статуса/тем/ролей. Для решения AI в текущем диалоге локальные attributes + pending sync + его управляемые labels + private note фиксируются одной транзакцией. Fan-out на другие активные диалоги асинхронный; в каждом из них labels и соответствующая note сохраняются вместе. Не обещаем общую транзакцию с Klaviyo или со всеми диалогами. Удалённая синхронизация подтверждается отдельно: заметка о локальном изменении не утверждает, что Klaviyo уже обновлён. Private notes не являются входящим доказательством, не вызывают @shumabit и не генерируют маркетинговые события. Заметка — снимок на момент записи со временем проверки; актуальные значения находятся в атрибутах и последних применённых проекциях активного диалога.

## 6. Точные направления синхронизации

| Данные | Направление и правило |
|---|---|
| Покупки, оплата, возврат | Shopify → существующие финансовые процессы/нативный Klaviyo sync. Chatwoot получает контекст; AI/оператор не меняют факт оплаты через поле CRM |
| Paid lifecycle/count/coverage | Существующий paid-history job → Klaviyo properties → локальная проекция контакта Chatwoot. Это один расчёт, не второй алгоритм по orders_count |
| VIP/Influencer/Model/Wholesale/High value | Именованные свойства профиля Klaviyo ↔ четыре поля единственного связанного контакта Chatwoot. Редактирование возможно с обеих сторон; далее локальные attributes → customer labels активных диалогов, без обратного чтения лейблов |
| Sales status | Владелец Chatwoot; в Klaviyo экспортируются определённые события, не редактируемое зеркало стадии каждого диалога |
| Intent/support topics | Владелец Chatwoot. В первом этапе оставляем там; существующее qualification-событие сообщает квалификацию. Копирование всех тем в Klaviyo не требуется для запуска. Если позднее нужна аудитория по теме, добавляем versioned conversation-event properties, не общий профильный intent и не обратную запись тем |
| Сегменты Klaviyo | Вычисляются из фактов/свойств. Вход/выход из сегмента сам по себе не равен пользовательской правке роли. Для автоматического VIP нужна явно заданная бизнес-логика |
| Лейблы/значки → Shopify | Не копируем. Shopify уже даёт коммерческие факты; создание набора CRM-тегов там не решает требование операторской видимости |
| Meta | Только подходящие подтверждённые события существующего exporter. Ни VIP, ни сам label-qualified не являются CAPI-сигналом |

Используем существующий Klaviyo client и job infrastructure. Новый сервис/коннектор и универсальная двусторонняя шина не нужны. Изменение Chatwoot ставит адресный update в очередь; чтение Klaviyo обновляет локальное зеркало и не вызывает повторную отправку. Перед записью читаем актуальные поля, после — проверяем сохранение. В нормальном режиме целевое отставание Klaviyo → Chatwoot не более 15 минут; ошибка видима. Простое открытие интерфейса — read-only; входящий диалог/плановый job обновляет данные в фоне.

Записываем только пять согласованных свойств ролей, сохраняем сторонние properties и согласия на рассылку. true и false передаются оба, отсутствующее значение не превращается в false. Pending local edit защищён от старого снимка. AI применяет yes только к unknown; обнаруженный до отправки явный remote false отменяет ожидающий AI-positive. Наши записи для одного профиля последовательны. Храним per-field baseline последнего подтверждённого общего значения и pending revision. Remote=baseline позволяет отправить pending; remote=pending подтверждает его; remote отличается от обоих — конфликт. При конфликте явных ручных правок принимаем текущее Klaviyo value, отменяем pending и пишем одну private note; не заявляем знание wall-clock порядка. Без baseline явный remote value первичен; при его отсутствии отправляем обоснованную локальную роль. Перед подтверждением проверяем identity/revision. Прямое внешнее изменение между GET/PATCH остаётся ограничением API без compare-and-set.

Существующая связь — один Klaviyo profile ↔ один канонический Chatwoot contact. У контакта могут быть разные ContactInbox и диалоги на нескольких каналах. Два отдельных контакта не объединяются по имени автоматически; требуется разрешить личность существующим процессом. При смене/снятии связи старые внешние факты инвалидируются, а принадлежавшие неверной связи customer labels снимаются по правилу исправления идентичности из §3.1, а локальные role-правки не переносятся молча на другого покупателя.

## 7. Автоматизация первого этапа и shadow

**Shadow — AI выполняет оценку и сохраняет предложенные status/topics с причиной, но не меняет рабочие атрибуты/лейблы и не создаёт из своего предложения бизнес-события квалификации/оплаты или внешние Meta/Klaviyo-конверсии. Внутренние записи оценки classification_evaluated сохраняются намеренно, включая предлагаемые роли после расширения схемы.** Это не «AI ничего не делает» и не общий выключатель интеграций: действующие Shopify-проекции, ручные изменения и их экспорты продолжают работать по своим правилам. Shadow-выводы не пишем как будто применённые изменения в клиентский timeline.

Проверка сейчас не завершена: исправляем контекст тестовых диалогов, добавляем известную историю покупателя отдельно от текущей покупки, сохраняем ранее оставленные замечания. Затем показываем готовые оценки, пользователь отмечает только ошибки и объясняет их. Это проверка модели/инструкции на примерах, не обучение весов модели и не ежедневная модерация каждого сообщения.

После согласования проверенного набора включаем auto на pilot inbox 2 (FB/Instagram). Тогда AI самостоятельно применяет стадии, темы и допустимые положительные признаки; оператор исправляет только ошибки. Уверенности нет → не делаем позитивный вывод и показываем причину неопределённости. Свежесть доказательств, защита Shopify-статусов и ручных исправлений сохраняются. Настройка новых диалогов WhatsApp/LINE уже изменена, но не означает включения классификатора на этих каналах.

В этапе 1: управляемые лейблы и private summary notes в штатном UI, сопоставление при работе с текущими контактами, автоматические status/topics и influencer/wholesale, двусторонние пять свойств, buyer-history projection, служебные заметки, проверка качества и фактическая активация auto. Не считаем этап законченным на создании пустых полей.

VIP/high-value остаются ручными назначениями с автоматической синхронизацией. При миграции разово назначаем VIP всем текущим подтверждённым Repeat (42 на 29 сентября); это не постоянное правило второй покупки. High-value отдельно не выводим из VIP или Repeat. В этапе 2: массовая разметка архивов, сравнение Sonnet, отдельный influencer-management процесс, публичные ответы/создание заказов Shumabit. Нет нового permission framework.

## 8. Приёмка: что должно быть доказано

- Согласованный набор атрибутов даёт точный набор десяти управляемых labels в новом, существующем активном и переоткрытом диалоге. client → repeat никогда не оставляет оба lifecycle labels.
- Изменение yes → no → unknown, включая Klaviyo-origin change, обновляет attributes и активные labels; старый queued job не восстанавливает снятый признак. Обычные темы/spam/source при проекции сохраняются.
- На реальном рабочем iPhone и web проверяем отображение стандартных меток, полный доступ к private note и поведение штатной ошибки при попытке редактирования управляемых значений. Не обещаем видимость всех меток в одной строке.
- Редактирование contact enum поддерживается штатным используемым клиентом или доступно в существующей веб-карточке. Сервер отклоняет ручную порчу paid fields и managed labels, но принимает обычную правку темы с неизменными managed labels.
- Pending/snoozed считаются активными. Закрытие одновременно с отложенной проекцией сохраняет определённый snapshot; обычное изменение VIP не переписывает resolved, переоткрытие актуализирует; исправление ошибочной связи очищает именно её ошибочные customer labels, включая resolved.
- Одновременная обычная правка темы и customer projection сохраняет обе успешные правки; устаревший полный список с изменившимися управляемыми customer labels явно отклоняется. Проверка проходит через штатный API/bulk-путь, а не только внутренний service. Штатный API передаёт labels[] без версии: две одновременные правки только обычных тем разными клиентами сохраняют native last-writer поведение. В первом этапе для одного оператора не вводим новый протокол или мобильный форк; защиту от потери между двумя такими topic-only правками не обещаем.
- Исправление identity использует сохранённого владельца проекции: не удаляет снимки другой корректной связи; удаление устаревших меток без происхождения выполняется отдельной согласованной структурной миграцией.
- Первый запуск сохраняет прежние customer labels в private migration manifest, удаляет legacy во всех statuses и проецирует текущие факты только в активное подмножество; нет молчаливого импорта в Klaviyo и массовой AI-разметки архивов.
- Несопоставленный клиент не становится non_buyer; timeout/stale не выдаётся за отрицательный факт. Частичная история с >=2 оплатами означает «не менее 2» и Repeat.
- Новый support-only диалог Repeat/VIP не создаёт qualified/purchased; прошлые покупки остаются контекстом. Draft/TBYB/unpaid pickup не дают paid.
- Снятая оператором ошибочная тема не возвращается на старом доказательстве. Mention/tag и просьба о скидке не дают ложные influencer/wholesale. Явный no не переопределяется AI.
- Одна сводка на новый диалог/сопоставление/материальное изменение; ни одной при простом открытии или неизменном refresh. Локальная note не заявляет об уже успешной remote delivery. Повторные jobs не создают дубликаты.
- Ошибка первой summary note не откатывает входящее сообщение; повтор job после восстановления создаёт ровно одну заметку.
- Изменение проекции не запускает sync/classification/conversion снова. При ошибке заметки не остаётся молча применённого AI-изменения. Исправление identity не переписывает замороженные продажи.
- Shadow сохраняет диагностические оценки, но не применяет AI-выводы. Shopify/manual writers и их управляемые проекции работают независимо. Auto включается после correction-only quality review на pilot inbox 2.
- Первая реальная двусторонняя запись/readback Klaviyo и фактические приватность/рендер notes обязательны. Юнит-тесты не заменяют UI и provider acceptance. Согласия на рассылку не меняются.

## 9. Реализация и альтернативы

Порядок внутри первого этапа: (1) словарь типов/managed labels и прекращение устаревших native rules; (2) verified buyer projection и защита записей; (3) sync пяти свойств, timestamps и pending state; (4) локальная проекция в новые/активные/reopened диалоги и notes; (5) расширенный classifier и регрессии исправлений; (6) качество, реальный mobile/web readback, auto activation. Не считаем задачу законченной на пустых полях или вечном shadow.

Новая backend-логика находится в umi/ overlay и использует имеющиеся jobs/clients. Точки интеграции: Umi::Funnel::{Configuration,ConversationProjection,ClassificationClient,ConversationClassifier,ProfileBinding,KlaviyoClient}, существующие contact/conversation callbacks и label update/bulk пути. Повторно используем buyer-lifecycle.mjs из infra, не создаём второй алгоритм оплат. Для фактов и notes модель не нужна; LLM используется только для оценки смысла сообщений. Новая frontend-панель не нужна. Единственное выявленное исправление штатного редактора — await contact update/delete и отображение ошибки вместо преждевременного success; layout не меняется.

Альтернативы: «всё лейблами» не различает unknown/no, суммы и даты; «только атрибуты» прячет быстрый контекст в стандартной очереди; новая Vue-сводка не помогает штатному native приложению и отклонена пользователем. Выбор: атрибуты — истина, темы — обычные labels, десять customer labels — управляемое отображение, private note — полная сводка. Это ограниченная односторонняя проекция, не универсальная двусторонняя синхронизация всех тэгов.
